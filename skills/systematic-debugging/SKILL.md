# Systematic Debugging

## 铁律

**没有完成根因调查，不要提出修复。**

症状修复不算修复。先回答“发生了什么、为什么发生”，再谈改哪里。

## 四个阶段

### 阶段 1：根因调查

在改任何代码之前：

1. **完整读错误**：错误消息、堆栈、退出码、行号、文件路径。不要只看最后一行。
2. **稳定复现**：能否每次触发？最小复现步骤是什么？不能复现就继续收集信息，不要猜。
3. **检查最近改动**：`git diff`、最近提交、依赖变化、配置变化、环境差异。
4. **多组件系统在边界取证**：如果链路是 TUI → agent → provider → 工具 → 文件系统，先在每一层边界加日志或打印，确认数据在哪一层开始不对。
5. **追数据流**：坏值从哪里产生？谁把它传进来？一路向上追到源头，在源头修，不在症状处修。

本项目常用取证位置：

- `data/logs/agent.log`：结构化运行日志；
- `data/logs/turns/*.json`：每轮消息、工具耗时、token、结束原因；
- `data/sessions/`：会话事件，可回放；
- `shell` 跑 `go test ./...`、`go vet ./...`、`go build ./...`，保留完整输出。

### 阶段 2：模式分析

1. 在代码库里找**能正常工作的相似实现**。
2. 如果参考的是外部实现或文档，完整读完，不要只扫一眼。
3. 列出“能工作”和“不工作”之间的**所有差异**，再小的差异也列出来。
4. 确认依赖：配置、环境变量、工具版本、权限、路径。

### 阶段 3：假设与最小验证

1. 只提出**一个**假设，写成“我认为 X 是根因，因为 Y”。
2. 做**最小**改动验证假设，一次只动一个变量。
3. 验证通过 → 进入阶段 4；不通过 → 提出新假设，不要在旧修复上继续叠。
4. 不知道就说不知道，先补信息，不要装懂。

### 阶段 4：实施

1. **先写失败测试**：最小复现，优先自动化；没有测试框架就写一次性脚本。
2. **只做一个修复**：针对根因，不夹带重构，不“顺手改一下”。
3. **验证**：测试通过、相关测试不回归、原始症状消失。
4. **修复无效**：停下来数一数。如果已经试了 3 次以上，不要再试第 4 次，转为质疑架构。

## 三次失败后质疑架构

出现下面这些信号，说明不是假设错，而是结构有问题：

- 每修一处，就在另一个地方冒出新共享状态或新耦合；
- 修复需要“大改”才能落地；
- 每修一次就产生新的症状。

这时停下来，和用户讨论：这个设计是否根本成立？是继续修症状，还是改结构？

## 红旗

出现下面任何一句，回到阶段 1：

- “先快速修一下，之后再查。”
- “大概是 X，先改这个。”
- “一次改几个地方，跑一下测试看看。”
- “跳过测试，我手动验证过。”
- “我不完全理解，但这样可能行。”
- “再试一次。”（已经试过两次以上）
- “每个修复都冒出新问题，但继续修。”

## 常见借口

| 借口 | 现实 |
|---|---|
| “问题很简单，不用流程” | 简单问题也有根因；流程在简单问题上更快。 |
| “很急，没时间调查” | 猜着改比系统排查更慢，返工更多。 |
| “先试一下，不行再查” | 第一个修复会定下错误方向。 |
| “修完再补测试” | 没先失败的测试，证明不了修的是对的。 |
| “一次改多个地方省时间” | 无法隔离哪个改动生效，还会引入新 bug。 |
| “参考太长，我按理解改” | 部分理解必然漏掉边界。 |

## 完成标准

- [ ] 能说清根因：坏值/坏状态从哪来，为什么到这里才暴露
- [ ] 有失败测试或可重复的复现步骤
- [ ] 修复只针对根因，没有夹带无关改动
- [ ] 原始症状消失，相关测试通过
- [ ] 跑了完整测试集，没有回归
- [ ] 如果是环境/时序问题，已记录排查过程并加日志或超时处理
