> 案例：`rainy-night-konbini`（雨夜便利店 · 3D）性能优化任务，版本 v35 → v62。
> 本文记录该次会话中 **0 次**调用技能的事实、原因、代价，以及自查发现的汇报失真。

## 3. 原因分析

### 3.1 执行层：判断环节被整体跳过（主因）

系统提示的措辞是「判断适用时先调用 `skill_load`」，把"是否适用"的判断权交给 agent。本次在收到"继续做优化"后，直接进入 `fs_read` 读文件，**没有执行这个判断**。

技能目录自己写着"不要凭猜测"，而我恰恰是凭猜测认定"这个任务不需要技能"。这不是技能库的问题，是流程执行缺了一步。

### 3.2 描述层：动词与任务形态错位

- `systematic-debugging` 的描述把触发条件限定在"构建失败/测试失败/运行时报错"。本次是**性能优化 + 视觉产出**，字面上一个词都不命中，需要一次语义延伸（"指标与预期相反"也属于行为不符合预期）才能对上。
- `verification-before-completion` 的描述其实**已经命中**（"汇报状态之前"），但我把它读成了"跑测试的时候才需要"——把技能正文里的**工具类型**（`go test`）误当成了**触发条件**。这是典型的把手段当门槛。

### 3.3 覆盖层：缺少实时渲染领域的技能

6 个技能全部是"怎么工作"的流程技能。`frontend-design` 管版式、视觉方向与设计系统；`web-report` 管数据可视化；**没有一个覆盖 canvas / WebGL 逐帧绘制的性能排查方法**。这一块属于真实缺口，不应假装技能库已经具备。

### 3.4 不是原因：技能不贴合本项目

反证如下（`verification-before-completion` 正文原文）：

- 列出的命令是 `go test ./...`、`go vet ./...`、`go build ./...`、`go test ./internal/tui`、`UPDATE_GOLDEN=1 go test ./internal/tui`、`go run ./cmd/agent doctor` —— 全是本仓库的命令；
- 还专门写了「涉及页面时：拿到预览地址并实际打开；375px 与桌面都不溢出」——正是本次任务的验收项。

**结论：技能与本项目贴合度不是问题，不能作为未调用的借口。**

## 5. 证据缺口（自查发现的汇报失真）

本节是对上一轮汇报的更正，需与本文一并阅读：

1. **JS 占比数字报错**。汇报称"JS 执行 6.2%（250ms/4s）→ 3.8%"。首次 profile 实际输出为：`total 4022ms`、`(program) 90.8% / 3652ms`、`(idle) 4.6% / 185ms`，据此 JS 约 **185ms ≈ 4.6%**；优化后为 155ms。真实降幅约 **16%**，不是"250 → 155"。此处用推断替代了读数。
2. **`createRadialGradient` 缺 before 数据**。第一次 profile 未单独统计渐变构造耗时，该指标只在优化后的 `prof2` 脚本里才加入。因此"消除了 radial 渐变热点"只有 after 证据，没有 before 对比。
3. **两次 profile 口径不完全可比**。首次 `(idle)` 占 4.6%、`(program)` 90.8%；后续 `(program)` 升到 96.1%，其中一部分来自 idle 消失而非真实优化。
4. **FPS 不可作为判据**。headless Chromium 走 SwiftShader 软件渲染，实测 `1440×900 → 41.5fps` 反而高于 `1152×720 → 35fps`，即降低分辨率更慢。任何"帧率提升 X%"的说法在本环境都不成立。
5. **未覆盖项**：未在真实 GPU 环境验证；未肉眼确认光晕改为贴图缩放后的边缘质量。

**净结论**：改动方向（减少每帧对象创建、缓存静态层）有 profiler 支撑；"变快多少"没有可信量化。汇报时未把这一区分讲清楚。

## 6. 改进意见

### 6.1 行为约定：任务动词 → 必查技能

| 听到这类词 | 先做 |
|---|---|
| 继续 / 优化 / 完善 / 加快 / 打磨 | 判断技能；性能类任务默认 `systematic-debugging` |
| 完成 / 修好了 / 通过了 / 汇报状态 | 必加载 `verification-before-completion` |
| 做页面 / 重做 / 改视觉 | `frontend-design`（有真实数据再加 `web-report`） |
| 报错 / 失败 / 不对 / 奇怪 / 先试一下 | `systematic-debugging` |
| 新增功能 / 改行为 / 重构 | `test-driven-development` |
| 新建或改 `SKILL.md` | `skill-creator` |

原则：**任务动词落在上表任一行，就先 `skill_load` 一次**。成本一次工具调用，收益是省掉 3–4 个废版本。

### 6.2 技能库修改建议

1. `systematic-debugging`：description 增补触发词「性能退化、响应变慢、指标与预期相反、准备先试一下」。
2. `verification-before-completion`：description 明确「任何对外汇报状态之前（不限于测试）」；正文新增一条硬规则——**汇报里的每个数字必须能在本次命令输出里找到出处，禁止二次推算**（针对§5 第 1 条）。
3. 新增 `realtime-canvas-perf` 技能，大纲：
   - 可信判据的选择：何时用 profiler 而非 FPS；
   - CDP `Profiler.samplingInterval` 读法：`(program)` 光栅化 vs JS 执行占比；
   - 软件渲染陷阱：SwiftShader 下 FPS 与分辨率反向；
   - 高频手法：radial 渐变贴图化、渐变分档复用、投影三角函数按帧缓存、静态层离屏化；
   - 自适应画质的滞回区间与"降档有效性校验"；
   - 验收：必须给出 before/after 同口径数据，或明确声明"无 before 数据"。

### 6.3 系统提示建议

把「判断适用时先调用 `skill_load`」改为硬规则形式，例如：

> 任务涉及 {优化, 修复, 完成声明, 新增功能, 重做页面} 中任一动作时，**必须先 `skill_load` 至少一个相关技能再做第一个动作**。

现有措辞把判断完全交给执行方，缺少最低强制项。

### 6.4 验收标准（可检查）

- [ ] 一次优化类任务中，`skill_load` 调用次数 ≥ 1；
- [ ] 汇报中每个数字可在本次命令输出中 `grep` 到；
- [ ] 未覆盖项在汇报中单列，不用"应该/大概"包装；
- [ ] 中间态版本（如 v59）在继续修改前至少过一次语法或冒烟校验。

## 7. 附：本次可复用的检查清单

1. 改画布渲染前，先跑一次 profiler，确认瓶颈在光栅化还是 JS；
2. 每帧内不得出现 `createRadialGradient` / `createLinearGradient` 的大面积调用；
3. 静态内容（货架、门贴、招牌）离屏缓存，主循环只 `drawImage`；
4. 自适应画质必须双向 + 滞回 + 降档有效性校验，否则会一路降糊；
5. 声明完成前，桌面与 375px 各跑一次（无溢出、无控制台报错、动画确在动）；
6. 报告中的 before/after 必须同口径，缺一侧就明说缺。
